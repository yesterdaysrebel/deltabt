# Deploying DeltaBot to AWS

**Paper trading only.** The bot reads public market data and has no
order-placement capability. There are no exchange credentials anywhere in this
stack and none should ever be added — the *absence* of the capability is the
safety boundary, not a flag. Nothing in `infra/terraform/` can turn paper into
live: there is no secret, no parameter, and no IAM permission here that would
help.

The only secret involved is the PostgreSQL password, and it is generated by RDS
directly into Secrets Manager. It never enters this repository, Terraform state,
a GitHub secret, the Docker image, or a shell script.

---

## What gets built

```
GitHub Actions ──OIDC──▶ IAM role (no access keys, sessions expire in an hour)
                             │
                             ├─▶ Terraform ─▶ VPC · EC2 · RDS · ECR · CloudWatch · SSM
                             │
                             └─▶ docker build/push ─▶ ECR ─▶ SSM Run Command ─▶ EC2
```

| | |
|---|---|
| **One** EC2 instance | `t4g.small`, Amazon Linux 2023, arm64. Public subnet, **zero inbound rules** |
| **One** RDS PostgreSQL 16 | `db.t4g.micro`, private subnets, encrypted, 35-day backups, deletion protection |
| ECR | immutable tags, scan on push, keep the last 20 images |
| Access | SSM Session Manager. **No SSH key pair exists in this stack** |
| Logs | container stdout → CloudWatch via the `awslogs` driver |
| State | S3, versioned, encrypted, native `use_lockfile` locking |

**Not built, deliberately:** no NAT gateway, no load balancer, no EKS, no
autoscaling group, no DynamoDB lock table, no bastion. Each is priced and
justified in [section 11](#11-approximate-monthly-cost).

`terraform fmt`, `terraform validate` and the destructive-plan guard run in CI on
every pull request; `scripts/tf_cost_preview.py` prints what a plan will create
and flags anything expensive before a human approves it.

## 1. AWS prerequisites

| | |
|---|---|
| An AWS account | a **dedicated** one is strongly preferred — the blast radius of a mistake stays inside it |
| Admin credentials **once**, on your workstation | only to run the bootstrap stack. CI never gets them |
| A region | default `ap-south-1` (Mumbai) — closest to the India venue, so websocket latency is lowest |
| Terraform ≥ 1.10 | for native S3 state locking. Below that you need a DynamoDB lock table; see [section 3](#3-terraform-bootstrap) |
| Docker + `aws` CLI v2 locally | only for manual operations |

Service quotas: a fresh account has all of these by default. No quota increase is
needed.

```bash
aws sts get-caller-identity      # confirm which account you are about to build in
```

Read that output before continuing. Building this in the wrong account is the
single easiest mistake to make here.

## 2. GitHub OIDC setup

There are **no** `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` secrets. GitHub
presents a short-lived OIDC token; AWS exchanges it for a session that expires
within the hour. There is no long-lived credential to leak, rotate, or forget.

Three roles, deliberately separated:

| Role | Trusted subject | Can do |
|---|---|---|
| `deltabt-github-plan` | `repo:ORG/REPO:pull_request` | read everything, change nothing (plus the state lock) |
| `deltabt-github-deploy` | `refs/heads/master` **or** `environment:paper` | manage this stack's infrastructure |
| `deltabt-paper-github-app-deploy` | `refs/heads/master` **or** `environment:paper` | push an image, run one SSM document. **Cannot touch infrastructure** |

The `sub` condition is what makes this safe. Without it, *any* GitHub repository
in the world could assume the role. A trailing `:*` would let any branch or pull
request in *this* repository do it — which is why the pull-request plan role is
separate and read-only.

After the bootstrap apply, set these as **repository variables**
(Settings → Secrets and variables → Actions → *Variables*, not Secrets — none of
them is secret):

| Variable | From |
|---|---|
| `AWS_REGION` | e.g. `ap-south-1` |
| `TF_STATE_BUCKET` | bootstrap output `state_bucket` |
| `AWS_TERRAFORM_ROLE_ARN` | bootstrap output `github_terraform_role_arn` |
| `AWS_TERRAFORM_PLAN_ROLE_ARN` | bootstrap output `github_plan_role_arn` |
| `AWS_DEPLOY_ROLE_ARN` | main-stack output `github_deploy_role_arn` |
| `SSM_DEPLOY_DOCUMENT` | main-stack output `ssm_deploy_document` |
| `BOT_INSTANCE_ID` | main-stack output `instance_id` |
| `ECR_REPOSITORY` | `deltabt` |
| `ALARM_EMAIL` | optional |

Also create an **environment** named `paper` (Settings → Environments) and add
yourself as a required reviewer. That environment gate is what makes every
infrastructure change and every deploy a deliberate human decision rather than a
side effect of a merge.

## 3. Terraform bootstrap

Chicken-and-egg: the main stack stores state in S3, but the bucket has to exist
first. So the bootstrap stack runs **once, by a human, with local state**.

It is deliberately not wired into CI. A workflow that can create its own trust
anchor can also replace it.

```bash
cd infra/terraform/bootstrap
terraform init
terraform apply \
  -var="github_org=YOUR_ORG" \
  -var="github_repo=deltabt" \
  -var="state_bucket_name=deltabt-tfstate-<something-globally-unique>"
```

Creates: the state bucket (versioned, encrypted, public access blocked,
`prevent_destroy`), the GitHub OIDC provider, and the plan/deploy roles.

**Keep `terraform.tfstate` from this directory.** It is small and its resources
never change. If it is lost, recover by importing rather than re-applying:

```bash
terraform import aws_s3_bucket.state              deltabt-tfstate-...
terraform import aws_iam_openid_connect_provider.github \
    arn:aws:iam::<account>:oidc-provider/token.actions.githubusercontent.com
terraform import aws_iam_role.github_deploy       deltabt-github-deploy
terraform import aws_iam_role.github_plan         deltabt-github-plan
```

**If you are stuck on Terraform < 1.10**, `use_lockfile` does not exist. Add a
DynamoDB table to the bootstrap stack and a `dynamodb_table` argument to
`backend.tf`. Do not simply drop locking — two concurrent applies against one
state file corrupt it.

**Never create a second state backend.** If `terraform init` reports the bucket
does not exist, the answer is to run the bootstrap stack, not to point the
backend somewhere else.

## 4. First infrastructure creation

```bash
cd infra/terraform
terraform init \
  -backend-config="bucket=$TF_STATE_BUCKET" \
  -backend-config="region=ap-south-1"

terraform plan -out=tfplan \
  -var="github_org=YOUR_ORG" -var="github_repo=deltabt"

# What this will cost, and whether anything expensive crept in
terraform show -json tfplan > tfplan.json
python3 ../../scripts/tf_cost_preview.py tfplan.json

# Refuse the plan if it destroys or replaces anything holding data
python3 ../../scripts/tf_guard.py tfplan.json

terraform apply tfplan
```

RDS takes roughly ten minutes. When it finishes:

```bash
terraform output
```

Feed those outputs into the repository variables from [section 2](#2-github-oidc-setup).

**No bot is running yet, and that is correct.** The instance boots with a systemd
unit that is *enabled but not started*, because no image tag exists. The first
deploy provides one.

### Resources that already exist but are not in Terraform state

Every resource here is explicitly **named** (`deltabt-paper-*`), so a create
against an existing resource **fails** rather than adopting or replacing it:

```
EntityAlreadyExists: Role with name deltabt-paper-instance already exists
DBInstanceAlreadyExists / RepositoryAlreadyExists / BucketAlreadyOwnedByYou
```

**Do not delete it in the console and re-run.** Import it:

```bash
terraform import aws_iam_role.instance         deltabt-paper-instance
terraform import aws_ecr_repository.bot        deltabt
terraform import aws_db_instance.main          deltabt-paper
terraform import aws_instance.bot              i-0123456789abcdef0
terraform import aws_cloudwatch_log_group.bot  /deltabt/paper/bot
```

`scripts/aws_unmanaged_check.py` runs in CI before every plan and detects this
situation up front — including the case Terraform *cannot* see, a second EC2
instance tagged for this environment. It never deletes anything; it prints the
import command and exits non-zero.

## 5. Subsequent deployments

Ordinary flow: **merge to `master`.**

| Workflow | Trigger | Does |
|---|---|---|
| `test.yml` | every push and PR | paper-only AST scan first, then the full suite against a real PostgreSQL, then the frozen-hash check, then `terraform fmt`/`validate` |
| `infrastructure.yml` | PR or push touching `infra/**` | OIDC → `fmt` → `validate` → unmanaged-resource check → `plan` → destructive-plan guard → cost preview → **approval** → apply the *saved* plan |
| `deploy.yml` | push to `master` | tests → build arm64 → push to ECR tagged with the git SHA → **approval** → SSM deploy → verify → print provenance |

Three properties worth knowing:

- **The image tag is always the git SHA, never `latest`.** ECR tags are
  immutable. A forward test whose results cannot be tied to an exact commit is
  not a forward test, and the tag is the only durable link between a database row
  and the code that produced it.
- **`apply` runs the plan file that was reviewed**, not a fresh plan. What you
  approved is what happens.
- **The forward experiment is never started automatically.** See
  [section 13](#13-how-to-start-the-forward-experiment).

Deploying while an experiment is running changes the code underneath it. The
workflow warns; it does not block, because a genuine bug fix mid-run is
sometimes necessary. The correct procedure is: stop the experiment, deploy,
start a **new** experiment id. A run whose code changed underneath it is two
experiments wearing one name.

## 7. How to restart EC2

```bash
# restart just the bot (preferred — seconds, and the database is untouched)
aws ssm send-command --instance-ids <id> --document-name AWS-RunShellScript \
  --parameters 'commands=["systemctl restart deltabt"]'

# reboot the host
aws ec2 reboot-instances --instance-ids <id>
```

The bot recovers open positions, cooldown state, realised PnL and the experiment
binding from PostgreSQL on start; it never fabricates exits for the gap. The
systemd unit is `enabled`, so a reboot brings it back with no human involved.

**Replacing the instance entirely** — because it is broken, or to resize it:

```bash
terraform taint aws_instance.bot     # or change instance_type
terraform apply
```

`disable_api_termination` prevents an accidental console termination, and
`tf_guard.py` refuses the plan in CI unless `ALLOW_REPLACE=1` is set
deliberately. The database is a separate resource and is untouched. After the
replacement, update the `BOT_INSTANCE_ID` repository variable and run the deploy
workflow to put an image back on it.

**The forward-test data survives all of this.** It is in RDS, not on the
instance. That is the whole reason for the split.

## 8. How to roll back

The previous tag is kept on the host in SSM Parameter Store and, more
importantly, the deploy **rolls back by itself**: if `/readyz` does not pass
within 15 minutes the host restarts the previous image without waiting for a
human.

To roll back deliberately:

```bash
# find the tag you want
aws ecr describe-images --repository-name deltabt \
  --query 'sort_by(imageDetails,&imagePushedAt)[-10:].[imageTags[0],imagePushedAt]' --output table

# what is running now, and what it would roll back to
aws ssm get-parameter --name /deltabt/paper/image_tag          --query Parameter.Value --output text
aws ssm get-parameter --name /deltabt/paper/image_tag_previous --query Parameter.Value --output text
```

Then run the **deploy** workflow with `workflow_dispatch` and put that tag in
`image_tag`. It skips the build and rolls straight to the existing image.

Or from a shell on the host:

```bash
aws ssm start-session --target <id>
sudo /opt/deltabt/deploy.sh <tag>
```

Rolling back the *image* does not roll back the *database*. If a bad build wrote
bad rows, see [section 9](#9-how-to-restore-postgresql).

## 9. How to restore PostgreSQL

**Backup policy:** automated daily snapshots with **35-day** retention — chosen
to outlive a 30-day run — plus point-in-time recovery to any second within that
window, plus a final snapshot on deletion. `deletion_protection` is on and
`prevent_destroy` makes Terraform refuse to plan the destroy at all.

Restore to a point in time. **RDS always restores into a NEW instance**; the
original is never modified, which is what makes this safe to do under pressure:

```bash
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier deltabt-paper \
  --target-db-instance-identifier deltabt-paper-restore \
  --restore-time 2026-08-13T04:00:00Z \
  --db-subnet-group-name deltabt-paper \
  --vpc-security-group-ids <db security group id>
```

Then either point the bot at the restored instance (edit `DB_HOST` in
`/opt/deltabt/env` and `systemctl restart deltabt`) or, once you are satisfied,
rename so the restored instance takes the original's name.

From a snapshot instead:

```bash
aws rds describe-db-snapshots --db-instance-identifier deltabt-paper \
  --query 'sort_by(DBSnapshots,&SnapshotCreateTime)[-5:].[DBSnapshotIdentifier,SnapshotCreateTime]' --output table
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier deltabt-paper-restore \
  --db-snapshot-identifier <snapshot-id> \
  --db-subnet-group-name deltabt-paper
```

`scripts/backup.sh` and `scripts/restore.sh` still work for logical dumps and are
worth running once against a scratch database **before the experiment starts**.
An untested restore is a guess. `restore.sh` refuses a target that already holds
an experiment unless `FORCE=1`.

### The acceptance criterion

> If the EC2 instance disappears, I can recreate the infrastructure and restart
> the bot without losing the forward-test database.

```bash
terraform apply          # recreates the instance; RDS is a separate resource and is not touched
# update BOT_INSTANCE_ID, run the deploy workflow
```

The bot reattaches to the running experiment, recovers open positions and risk
state, and continues. Nothing is lost, because nothing that matters was ever on
the instance.

## 10. How to destroy infrastructure safely

**Do not run `terraform destroy` while an experiment is running.** The database
is the deliverable.

`prevent_destroy` on `aws_db_instance.main` and on the state bucket means a
plain `terraform destroy` **fails**, on purpose. To take it down deliberately:

```bash
# 1. Confirm no experiment is active.
aws ssm send-command --instance-ids <id> --document-name AWS-RunShellScript \
  --parameters 'commands=["docker exec deltabot python -m app forward-test status"]'

# 2. Snapshot the database, and verify the snapshot exists.
aws rds create-db-snapshot --db-instance-identifier deltabt-paper \
  --db-snapshot-identifier deltabt-paper-final-$(date -u +%Y%m%d)
aws rds wait db-snapshot-completed --db-snapshot-identifier deltabt-paper-final-$(date -u +%Y%m%d)

# 3. Also take a logical dump. Two formats, because a snapshot can only be
#    restored into RDS and you may want the data elsewhere.
./scripts/backup.sh

# 4. Only now: remove prevent_destroy from rds.tf, set
#    db_deletion_protection = false, and destroy.
terraform destroy
```

The state bucket keeps its `prevent_destroy` and must be emptied and deleted by
hand if you truly want it gone. That deliberate friction is the point.

## 11. Approximate monthly cost

ap-south-1 on-demand list prices. **An order of magnitude, not a quote** — check
the real bill in the first week.

| | ~USD/month |
|---|---|
| EC2 `t4g.small`, 24/7 | 12 |
| RDS `db.t4g.micro` + 20 GB gp3 + backups | 13 |
| EBS root, 20 GB gp3 | 2 |
| Elastic IP (billed even while attached) | 4 |
| CloudWatch logs + alarms + ECR at this volume | ~2 |
| **Total** | **~30–35** |

Free here: VPC, subnets, route tables, internet gateway, security groups, IAM,
SSM (Session Manager, Parameter Store standard, Run Command), the first ten
CloudWatch alarms, S3 state at this size.

### What was rejected, and what it would have cost

| | ~USD/month | Why not |
|---|---|---|
| NAT gateway | 32 + data | The bot needs *outbound* only. A public subnet with **zero ingress rules** gives that free; SSM works outbound-only, so there is nothing to reach inbound. "Public subnet" describes routing, not exposure |
| Load balancer | 18 | Nothing serves public traffic. The dashboard is reached through SSM port forwarding |
| EKS | 73 (control plane alone) | To orchestrate one container that must never run twice |
| Multi-AZ RDS | +13 | The bot is not a customer-facing service. Backups protect the data; a failover would protect ~15 minutes of availability nobody is watching |
| DynamoDB lock table | ~1 | Superseded by S3 native locking in Terraform 1.10 |
| VPC endpoints | 7 each per AZ | Only worth it if the instance moves off the public subnet |

Two savings taken: **arm64/Graviton** (~20% cheaper for the same work, and the
image is built for it) and `gp3` over `gp2`.

If you want to halve it: a 1-year no-upfront Savings Plan on the EC2 and RDS
instances, and drop `log_retention_days` from 90 to 30.

## 12. How to verify the bot is actually running

**Health here is a statement about DATA FRESHNESS, not about the process.** A bot
whose websocket died silently still answers TCP and still has a live event loop.
That is worse than a crash, because a crash restarts. Nothing in this AWS setup
replaces that semantic with a process check.

```bash
aws ssm start-session --target <id> --document-name AWS-StartPortForwardingSession \
  --parameters '{"portNumber":["8000"],"localPortNumber":["8000"]}'

curl -s localhost:8000/healthz | jq
curl -s localhost:8000/readyz  | jq
curl -s localhost:8000/api/status | jq
```

`/healthz` returns **200 only when all six hold**:

| check | means |
|---|---|
| `websocket_fresh` | a message arrived recently |
| `candles_fresh` | a 1m bar closed recently |
| `no_recent_gaps` | no missing candles in the recent window |
| `database_writable` | an actual write probe succeeded, not a SELECT |
| `strategy_running` | the engine is up |
| `evaluation_loop_alive` | **the loop itself reports when it last ran** |

That last one exists because a flag is not evidence: the evaluation loop once
died inside its own error handler while the process, the socket and the candle
builder all kept working, and every other signal stayed green.

From CloudWatch, without a tunnel:

```bash
# The most important question: is it saying anything at all?
aws logs tail /deltabt/paper/bot --since 10m | tail -20

# Exactly one container, and which image
aws ssm send-command --instance-ids <id> --document-name AWS-RunShellScript \
  --parameters 'commands=["docker ps --format \"{{.Names}} {{.Image}} {{.Status}}\""]'
```

Alarms that page you (if `alarm_email` is set):

| Alarm | Fires when |
|---|---|
| `bot-silent` | **nothing logged for 15 minutes.** The one that matters most — a dead evaluation loop logs no errors, so error-count alarms are silent for exactly that failure. `treat_missing_data = breaching`, so a bot that never starts is not silently green |
| `critical-events` | any `CRITICAL` — configuration drift, a lost advisory lock, a refusal to start |
| `error-rate` | >20 errors in 5 minutes, twice running |
| `restart-loop` | >3 process starts in 30 minutes |
| `db-no-connections` | no database connections for 15 minutes |
| `instance-status`, `disk`, `memory`, `db-storage`, `db-cpu` | the usual host and database conditions |

**Exactly one bot must run.** The PostgreSQL session advisory lock is the
authoritative guarantee — a second process refuses to start and exits — and
nothing in this infrastructure weakens it: one instance, no autoscaling group,
systemd as the single lifecycle owner (Docker's own restart policy is
deliberately unused, so two things never disagree about whether the bot is
running). `aws_unmanaged_check.py` additionally fails CI if a second tagged
instance appears.

## 13. How to start the forward experiment

**This never happens automatically.** No workflow, no user-data script, and no
Terraform resource starts an experiment or creates an experiment id. It is an
explicit human action, taken after a go/no-go decision.

First, all 16 preflight checks must pass:

```bash
aws ssm start-session --target <instance-id>
docker exec deltabot python -m app forward-test preflight
```

If **any** check fails: do not start. Fix it, redeploy, re-run preflight.

Then, and only then:

```bash
docker exec deltabot python -m app forward-test start --days 30
```

The experiment id defaults to `H-WPR-1-PAPER-<UTCDATE>`.
**`H-WPR-1-PAPER-20260813` must not be reused** — it is stopped and immutable,
retained as the artifact of the run that found the `max_open_positions` race.

During the 30 days, change nothing: no parameters, no risk limits, no symbols, no
filters, no manual intervention in individual trades. If a technical failure
occurs, stop the experiment, fix it, and start a **new** experiment id. Do not
silently patch and continue.

Daily report:

```bash
docker exec deltabot python -m app forward-test report --day "$(date -u -d yesterday +%F)"
```

## 14. Failure modes

| | What happens | Verified |
|---|---|---|
| **A. EC2 reboot** | systemd unit is `enabled`; the bot returns unattended and recovers positions, cooldown, PnL and the experiment binding from PostgreSQL | recovery logic tested locally; the AWS path needs an account |
| **B. Container crash** | `Restart=always`, `RestartSec=15`, `StartLimitIntervalSec=0` — it retries forever rather than giving up after five tries, because an outage lasting hours has to self-heal | restart semantics tested locally |
| **C. Network outage** | feed reconnects with backoff, gaps are detected and repaired, `/healthz` goes red then green. Measured: 47 loop errors during a 60-second outage, full recovery, no lost bars | verified locally |
| **D. PostgreSQL restart** | the pool reconnects; `database_writable` recovers; the bot does **not** restart and does not fabricate exits | verified locally |
| **E. Deploy failure** | `deploy.sh` restarts the previous tag automatically and the workflow exits non-zero | logic reviewed; needs an account |
| **F. Bad image** | `/readyz` never passes → automatic rollback → workflow fails | logic reviewed; needs an account |
| **G. Failed health check** | `/readyz` gates the rollback. `/healthz` is reported but **not** a rollback trigger — it is a statement about market data, and a candle gap seconds after a restart is not the image's fault | by design |
| **H. Plan shows unexpected destruction** | `tf_guard.py` fails the job before a human sees a green check. Override is `ALLOW_REPLACE=1`, printed loudly | **verified: refuses a database replacement, permits a benign update** |
| **I. Duplicate EC2** | `aws_unmanaged_check.py` fails on a second tagged instance; the advisory lock refuses the second bot regardless | guard logic verified; needs an account for the live query |
| **J. Resource exists but is not in state** | fixed names → Terraform errors instead of adopting. The check runs first and prints the exact `terraform import` line | **verified: fails safe, never destroys** |

Full application-level failure analysis is in [failure_modes.md](failure_modes.md).

## Appendix: what is deliberately absent

- **No exchange API credentials.** The AST safety scan in `test.yml` fails the
  build if an order-placement method, a credential identifier, a signing import,
  or a non-GET verb appears in `app/`. It is a gate, not a convention.
- **No SSH key pair.** Not "unused" — it does not exist. `admin_cidrs` defaults
  to empty and creates no ingress rule at all.
- **No database password in Git**, in Terraform state, in a GitHub secret, in the
  image, or in `docker inspect`. RDS generates it into Secrets Manager; the host
  fetches it at start into a root-only file on tmpfs.
- **No long-lived AWS credentials.** OIDC only.
- **No `latest` tag.**
- **No automatic experiment start.**

### One repository choice worth knowing

`.terraform.lock.hcl` is **not committed**. It should be, for provider-checksum
reproducibility — but the lock file in this working tree was generated against
the OpenTofu registry (the only tool available here) and committing it would
break `terraform init` for everyone else. Generate and commit a real one on the
first machine that runs Terraform proper:

```bash
cd infra/terraform
terraform providers lock -platform=linux_amd64 -platform=darwin_arm64
git add -f .terraform.lock.hcl
```

Until then, the provider is pinned by `~> 5.60` in `versions.tf`, which
constrains the minor version but not the checksum.
